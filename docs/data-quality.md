# Качество текущих данных

Проверка `assets/data/processed/data.json` (500 вопросов) на то, о чём пишет
raw.md: "там уже сейчас есть битые данные, такие как недостаток вариантов
ответов или отсутствие верного ответа".

## Что нашлось

- **Вариантов ответа всегда ровно 4** в текущем файле — это было завязано на
  UI телеграм-бота (4 кнопки — оптимально визуально), не фундаментальное
  ограничение. **Решено**: валидатор должен требовать 2–10 вариантов, не
  жёстко 4 — старые данные это ограничение не нарушают, но новые (со
  скрапинга) могут иметь другое количество.
- **2 вопроса, где правильный ответ не входит в список вариантов** (id 251 и
  372) — причина не "забыли добавить верный ответ", а повреждение кодировки:
  в `answer_options` часть русского "цу" превратилась в символ хангыля `츠`:

  ```json
  { "id": 251, "answer": "Мацумае", "answer_options": ["Ма츠yмае", "Кен Канеки", "Джузо Судзуя", "Котаро Амон"] }
  { "id": 372, "answer": "Тоору Муцуки", "answer_options": ["Тоору Му츠ки", "Сайко Йонебаяши", "Хаиру Ихей", "Кийоко Аура"] }
  ```

  Похоже на баг конкретно в пайплайне, которым генерировались/копировались эти
  два варианта (не связано с текущим Fandom-парсингом — надо проверить при
  новом скрапинге, не всплывёт ли та же порча кодировки).
- Дублей вариантов внутри одного вопроса — не найдено.

## Что уже умеет текущий загрузчик и чего не умеет

`src/services/questionsDataService.ts` сейчас:
- **падает** (не стартует сервер), если файл не парсится по zod-схеме или есть
  дублирующийся `id`;
- **только предупреждает в лог**, но не отклоняет вопрос и не останавливает
  загрузку, если: текст вопроса дублируется, или правильный ответ не входит в
  `answer_options` — то есть ровно два найденных выше битых вопроса сейчас
  молча отдаются викториной.

raw.md требует "никогда не отдавать неверные данные" — значит эти
предупреждения нужно превратить в жёсткую проверку.

**Решено**: любой вопрос, не прошедший валидацию, — это **fail-closed** отказ
запуска API целиком, как сейчас с дублирующимся `id`, а не пропуск битой
записи с отчётом в лог. Причина — иначе есть риск через пару месяцев получить
живой API, в котором *нет ни одного* корректного вопроса, и никто не заметит
вовремя.

## Что нужно для новых форматов

Валидаторы потребуются отдельно под каждый формат из
[question-types.md](question-types.md) — например, для `boolean`-вопросов
проверка "ровно два варианта `Да`/`Нет`" (если выберем такое представление)
или просто наличие поля `correct`; для медиа-вопросов — что `media.url`
доступен/не битый.
