# Типы заданий

## Что реально реализовано (расходится с гипотезой ниже)

Единую схему `type: choice | boolean, prompt: {text?, media?}` из раздела
"Задуманная матрица форматов" **не стали строить** — на практике решение по
п.4 в [open-questions.md](open-questions.md) оказалось «разные структуры»,
а не «одна схема с nullable-полями». Что реально есть в коде сейчас:

- **Текст + варианты, с опциональной иллюстрацией к ответу** —
  `src/services/questionsDataService.ts`. `answerMedia` просто добавлен в
  старую схему (`id/question/answer/answer_options/answer_group`), без
  `type`/`prompt`-обёртки.
- **Медиа + варианты ("кто/что это?")** — `src/services/whoisDataService.ts`,
  **полностью отдельный файл/сервис/эндпоинты** (`GET/POST /api/quiz/whois/*`),
  не вариант той же схемы. Причина: у медиа-вопроса нет текста, а основная
  схема требует уникальный текст вопроса (используется для поиска по тексту,
  `getByQuestion`) — тащить его в общую схему означало бы городить исключение
  из этой проверки специально для одного типа. Отдельный файл проще и честнее:
  у каждого формата — ровно те проверки, которые ему нужны.
- **Утверждение (да/нет)** и **медиа + утверждение (да/нет)** — не реализованы.

Вывод на будущее: если понадобится ещё один формат, вероятно стоит снова
заводить для него свой файл/сервис/эндпоинты (как `whois`), а не пытаться
дотянуть до одной общей схемы постфактум.

## Текущее поведение

Один формат: текстовый вопрос + 4 варианта ответа, без тем.

```json
{ "id": 158, "question": "...", "answer_options": ["...", "...", "...", "..."], "answer_group": "name" }
```

`answer_group` — это тип *ответа* ("name", "kagune_type", "rank", "color", ...),
не тема вопроса. Он уже неплохо совпадает с частью задуманных тем
("какой тип кагуне" ≈ `kagune_type`, "какой ранг опасности" ≈ `rank"), но не
покрывает всё (например, "чья цитата" — такой группы сейчас нет). См.
[topics.md](topics.md) про разницу между этим полем и темами.

## Задуманная матрица форматов

Из raw.md видно, что новые форматы — это не 4 произвольных типа, а комбинация
двух независимых осей:

| | **ответ: варианты** | **ответ: да/нет** |
|---|---|---|
| **вопрос: текст** | текущий формат (расширить темами) | "[утверждение] → верно?" |
| **вопрос: медиа** | "[фото/видео] → кто/что это?" + варианты | "[фото/видео] → верно, что это X?" |

Если это верно, у всех четырёх форматов может быть одна схема с нулируемыми полями,
а не четыре разные таблицы/модели. CheStor подтвердил часть деталей и добавил
требование про иллюстрацию к ответу (см. ниже), так что гипотеза сейчас выглядит так:

```ts
{
  id: number;
  type: "choice" | "boolean";       // формат ответа — boolean хранится как явное
                                     // поле `correct`, не как Да/Нет-варианты
  prompt: {
    text?: string;                  // текст вопроса/утверждения
    media?: { url: string; kind: "image" | "video" };
    hint?: string;                  // опционально; решено добавить в схему,
                                     // но заполнять руками пока не будем — барьер
  };
  topics: string[];                 // плоский список тегов, 1+; см. topics.md
  source: "anime" | "manga" | "both"; // пока открыто, см. open-questions.md
  // type === "choice"
  answer_options?: string[];        // решено: 2–10 вариантов, не жёстко 4
                                     // (4 было завязано на UI телеграм-бота)
  answer?: string;
  // type === "boolean"
  correct?: boolean;
  // общее для обоих type — иллюстрация к ПРАВИЛЬНОМУ ОТВЕТУ, см. ниже.
  // Нет отдельного флага "answer_type" — nullable `answerMedia` сам себе флаг.
  answerMedia?: { url: string; kind: "image" | "video" } | null;
}
```

Это рабочая гипотеза, не финальная схема — CheStor явно попросил не
воспринимать текущие 4 формата как конечный результат и делать схему легко
расширяемой под будущие форматы. Какой подход (общая схема с nullable-полями
vs discriminated union по `kind`, по одной структуре на формат) здесь лучше
для расширяемости — решим на этапе проектирования самой схемы.

## Нюансы по форматам из raw.md (решено)

- **Медиа + варианты ("кто/что это?")** — может иметь опциональную текст-подсказку
  (`prompt.hint`) одновременно с картинкой. Хорошая гейм-механика, но подсказки
  пишутся вручную — это барьер, поэтому поле в схеме есть, а заполнять его
  массово пока не будем.
- **Утверждение, да/нет** — булево поле `correct`. Единая норма по форматам не
  требуется (у `choice` свой набор полей, у `boolean` — свой).
- **Медиа + утверждение, да/нет** — `prompt.media` + `prompt.text` (формулировка
  утверждения) одновременно, `correct: boolean`.
- **"Чья цитата"** — обычный `choice`-вопрос с темой `quote_author`, 4 варианта —
  имена персонажей. Дословность самой цитаты — ответственность Fandom-вики как
  источника истины, API это не перепроверяет отдельным механизмом.

## Иллюстрация к ответу (новое, из raw.md)

Отдельно от медиа в `prompt` — медиа может быть и у *ответа*, чтобы клиент мог
наглядно показать правильный ответ, а не только текст. Пример из raw.md:

> вопрос: какой тип кагуне у Гуля? → ответ: Ринкаку → высылается: "Ринкаку" +
> фото этого гуля, где виден кагуне.

Для вопросов без подготовленного медиа ответ — всегда просто текст (нет
иллюстрации → нет поля/оно пустое). Это именно про `/api/quiz/answer`, а не про
`/api/quiz/random` — иллюстрация едет вместе с *правильным* ответом, который
сейчас отдаётся только после входа (`requireUser`).

Решено: отдельный enum-флаг не нужен (nullable `answerMedia` — сам себе
presence-флаг, лишние байты не нужны); у медиа-вопросов (`prompt.media` уже
показывает ответ) — `answerMedia` всегда пуст, отдельная иллюстрация к ответу
там избыточна. Переиспользуемый пул медиа vs выделенные картинки под ответ —
осталось открытым, см. [open-questions.md](open-questions.md).
