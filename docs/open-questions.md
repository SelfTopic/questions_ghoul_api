# Открытые вопросы

## Решено (CheStor ответил в raw.md)

1. Текст-подсказка у медиа-вопроса — **добавляем в схему как опциональное
   поле**, но фактически заполнять руками пока не будем (барьер по трудозатратам).
   См. [question-types.md](question-types.md).
2. Да/нет-задания — **булево поле `correct`**, не `answer_options`.
3. "Чья цитата" — **обычный `choice`-вопрос** с 4 вариантами имён персонажей;
   дословность цитаты — ответственность Fandom как источника истины, API её не
   перепроверяет.
4. Единая схема vs 4 отдельные структуры — **не фиксируем текущие форматы как
   финальные**, схема должна легко расширяться под новые форматы в будущem.
   Какой именно подход (общая схема с nullable-полями vs discriminated union
   по `kind`) легче расширять — решим на этапе проектирования схемы; CheStor
   не настаивает на конкретном варианте.
5. Темы — **обнаруживаются по ходу парсинга вики**, а не фиксированный
   захардкоженный список (слишком много тем, список изменять неудобно).
6. Тема на вопрос — **и то, и другое**: вопрос может иметь несколько тегов.
7. Иерархия тем — **нет, плоский список** (иерархия требует ручной настройки,
   это такой же барьер, как подсказки к фото — осознанно исключаем).
8. `answer_group` — **не источник истины**, нужен был только для MVP. Решение
   о его судьбе (убрать/переделать) принимается при проектировании новой схемы,
   но ориентироваться на него при дизайне тем/типов не стоит.

## Новое: иллюстрация к ответу (`answer_type`, из raw.md)

CheStor добавил требование: явный флаг, означающий, что́ именно возвращается в
ответе — помимо текста, может приезжать медиа, иллюстрирующее правильный ответ
(например, на вопрос "какой тип кагуне у Гуля?" с ответом "Ринкаку" — вместе с
текстом едет фото этого гуля, где виден кагуне). Для вопросов без
подготовленного медиа ответ — всегда просто текст.

Важно: это **не то же самое**, что медиа в `prompt` (медиа-вопрос "кто/что
это?"). Там медиа — часть *условия*, здесь — часть *ответа*. Концептуально
выходит, что и `prompt`, и ответ могут независимо нести необязательное медиа:

```
prompt: { text?, media? }
answer: { value, media? }   // media — иллюстрация к правильному ответу
```

Решено (ответы CheStor):

9. Отдельный enum-флаг `answer_type` **не нужен** — nullable `answerMedia` сам
   себе presence-флаг, лишние байты избыточны.
10. У медиа-вопросов типа "кто/что это?" **нет** отдельной иллюстрации к
    ответу — если иллюстрация уже есть в самом вопросе, в ответе она не нужна,
    `answerMedia` там всегда пуст.

Остаётся открытым:

11. Иллюстрация к ответу — тот же медиа-файл, что мог бы стоять в
    `prompt.media` у другого вопроса (переиспользуемый из общего пула медиа
    вики), или отдельная картинка под конкретный ответ? CheStor: "на первый
    взгляд кажется что да, но есть ощущение что в реальности может не
    сработать" — осознанно отложено до практики.

## Качество данных (data-quality.md) — решено

12. Битый вопрос (любой, независимо от причины) — **роняет запуск API
    целиком**, не просто выкидывается из набора с отчётом в лог. Причина:
    риск через пару месяцев получить живой API без единого корректного
    вопроса, и это не будет вовремя замечено.
13. Число вариантов для `choice` — **2–10**, не жёстко 4. Исходные 4 были
    завязаны на UI телеграм-бота (4 кнопки), это не фундаментальное
    ограничение.

## Источник: аниме / манга — решено

14. Нужны **оба** варианта: и фильтр по источнику при выдаче, и отдельные
    вопросы на знание различий аниме/манги. Проверено на реальных данных
    (см. [fandom-data.md](fandom-data.md)) — Fandom хранит это несколькими
    способами: категория `Anime-Only Characters`, отдельные секции «Manga
    Depiction» / «Anime Depiction» на странице персонажа, инлайн-пометки в
    инфобоксе, поля `manga debut`/`anime debut`, и у каждой цитаты —
    `ChapterRef` (манга) или `EpisodeRef` (аниме). Оба варианта реализуемы.

## Хостинг медиа — решено (на попробовать)

15. **Прямые ссылки на Fandom**, без рехостинга и без кэширующего прокси —
    пробуем так первым. Ноль новой инфраструктуры, согласуется с текущим
    минимализмом проекта (нет стораджа под бинарники, нестабильный интернет
    усложнил бы массовую синхронизацию картинок). Рехостинг/кэш-прокси —
    следующий шаг, если на практике всплывут конкретные проблемы (битые
    ссылки из-за правок вики, рейт-лимиты/блокировки по IP, хотлинк-защита).
    Менять решение потом дёшево — один клиент API, breaking changes разрешены.
